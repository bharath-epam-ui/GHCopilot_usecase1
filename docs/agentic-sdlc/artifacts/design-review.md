## Findings

### Completeness — FR Coverage

**FR-01 (Inline select permanently visible)**
Architecture section 6 specifies `<select data-testid="inline-status-select" aria-label="Change status">` as an unconditional element in the rendered JSX (not inside a conditional). Confirmed in working code at `components/TaskCard.tsx` line 104. No hover or toggle required. COVERED.

**FR-02 (All three options; current status pre-selected)**
Architecture shows all three `<option>` elements with correct `data-testid` values and human-readable labels. `value={optimisticStatus}` on the `<select>` drives pre-selection. Confirmed at lines 112–114. COVERED.

**FR-03 (PUT /api/tasks/:id on change)**
`handleStatusChange` in `app/dashboard/page.tsx` issues exactly one PUT with `body: JSON.stringify({ status: newStatus })` — no other fields included. Authorization header present. Confirmed at lines 113–120. COVERED.

**FR-04 (Card visual state updates; filter removes card)**
`<span data-testid="task-status" className="sr-only">{statusLabels[optimisticStatus]}</span>` contains the human-readable label (e.g., "In Progress"). After success, `fetchTasks(filter)` is called, which re-queries the API with the active filter and naturally drops the card if its status no longer matches. Confirmed at lines 100–102 and 125. COVERED.

**FR-05 (Rollback on non-2xx; inline error; auto-dismiss)**
`catch` block reverts `optimisticStatus` to `previousStatus`, sets `statusError`, and schedules `setTimeout(() => setStatusError(""), 3000)` (3 s, within the 5 s limit). `<p data-testid="inline-status-error">` renders when `statusError` is non-empty. Confirmed at lines 49–54. COVERED.

**FR-06 (Disabled while in flight)**
`setIsChangingStatus(true)` before `await`, `setIsChangingStatus(false)` in `finally`, `disabled={isChangingStatus}` on the `<select>`. Confirmed at lines 44, 53, 108. COVERED.

**FR-07 (Existing interactions unchanged)**
All nine existing `data-testid` values (`task-card`, `task-id`, `task-title`, `task-description`, `task-status`, `task-priority`, `task-assignee`, `edit-task-button`, `delete-task-button`) are present in the rendered output. `TaskForm.tsx` is not modified. Confirmed in implementation. COVERED.

**FR-08 (Unauthenticated change handled gracefully)**
The `try/catch` in `handleInlineStatusChange` covers all non-2xx responses including 401. `handleStatusChange` throws on `!res.ok`, which the catch intercepts. No unhandled promise rejections possible. Architecture section 4 explicitly enumerates 401, 404, and 500 handling. COVERED.

### Findings

**Finding DR-01**
- Severity: Low
- Location: `components/TaskCard.tsx` — `task-status` element; Architecture section 6, data-testid inventory table
- Issue: The existing `task-status` `data-testid` was on a visible, styled badge. The architecture moves it to a `<span className="sr-only">`, making it visually hidden. The guardrail ("never remove or rename existing `data-testid` attributes") is technically satisfied — the attribute and its `textContent` contract are preserved. However, any test that checks the badge for a visible CSS class or verifies it is not hidden would fail. This is a known, explicitly acknowledged tradeoff from OQ-01/Assumption D in `requirements.md`, but it represents a deliberate visual breaking change.
- Resolution: Confirm before Stage 5 that no existing manual test case in `manual-tests/test-cases.md` asserts the visibility or CSS class of `[data-testid="task-status"]`. If any test does, update the test (not the implementation) to assert on `[data-testid="inline-status-select"]` for visual status. No architecture change needed.

---

**Finding DR-02**
- Severity: Low
- Location: `components/TaskCard.tsx` lines 52–53 — `setTimeout(() => setStatusError(""), 3000)`
- Issue: The error auto-dismiss timeout has no associated cleanup. If the `TaskCard` component unmounts while the timeout is pending (e.g., a parent filter change removes the card from the list within 3 seconds of an error), the callback executes on an unmounted component instance. React 18 does not surface this as a warning, but it is an unnecessary execution and represents a minor resource leak.
- Resolution: No code change is required before Stage 4. As a low-priority follow-up, the timeout ID should be stored in a `useRef` and cleared in a `useEffect` cleanup function. This can be addressed in a future polish story.

---

**Finding DR-03**
- Severity: Low
- Location: `components/TaskCard.tsx` lines 46–48 — `if (onStatusChange)` guard; Architecture section 3, Assumption B
- Issue: When `onStatusChange` is not provided (test or Storybook contexts), the handler fires the optimistic update (`setOptimisticStatus(newStatus)`) but never rolls back, because the catch block is only reached if `onStatusChange` throws. The select remains on the new value until the parent provides an updated `task.status` prop. This is documented in Assumption B of `requirements.md` and is an accepted behavior, but the code contains no explanatory comment, which may surprise future contributors who add the component to a new context without the prop.
- Resolution: Add a one-line comment in `handleInlineStatusChange` adjacent to the `if (onStatusChange)` guard explaining that omitting the prop intentionally disables the API call and leaves the optimistic state in place. No functional code change required.

### Architectural Risks — Assessment

| Risk (from requirements.md) | Mitigated? | Notes |
|---|---|---|
| Race condition on rapid successive changes | Yes | FR-06 disables the control while a request is in flight; confirmed in implementation |
| Filter desync after inline status change | Yes | `fetchTasks(filter)` called on every success path in `handleStatusChange`; active filter passed at call time |
| Visual redundancy between status badge and select | Yes | `task-status` badge replaced by sr-only span; `<select>` is the sole visible status indicator |

**Additional risk not in requirements.md:**

`handleStatusChange` has a dependency on `filter` state. When the dashboard filter changes, `handleStatusChange` is recreated (the `useCallback` dependency array includes `filter`). This is correct because the callback calls `fetchTasks(filter)` and must capture the current filter value. However, a filter change causes all mounted `TaskCard` instances to receive a new `onStatusChange` reference on the same render, triggering a React reconciliation pass across all cards. This is harmless and expected with the chosen pattern; it is mentioned here for transparency, not as a defect.

## Decisions

The following design choices are confirmed at this stage:

1. `data-testid="task-status"` is retained on a `<span className="sr-only">` whose `textContent` equals the human-readable status label (e.g., "In Progress"). The visible status indicator is the `<select>` itself.
2. The `onStatusChange` prop on `TaskCardProps` defaults to a safe no-op (absent prop = no API call). This is the accepted contract for non-dashboard usages of `TaskCard`.
3. Inline errors auto-dismiss after 3 seconds (OQ-02 default assumption confirmed).
4. The dashboard re-fetches the full task list after every successful status change rather than updating local state only (OQ-03 default assumption confirmed). The optimistic update covers perceived latency.
5. The `handleStatusChange` callback is the sole issuer of the PUT request. `TaskCard` never calls `fetch` directly; it delegates to the prop and handles only UI state transitions.
6. `fetchTasks` in `app/dashboard/page.tsx` is already memoized with `useCallback([token, router])`, confirming it is a stable reference. The `handleStatusChange` `useCallback` dependency on `fetchTasks` does not cause instability.
