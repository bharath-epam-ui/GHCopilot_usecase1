## DR-06 Visibility Assertion Check

**Finding DR-06** (Low) from the design review required verifying whether any existing test
asserts `toBeVisible()` or `isVisible()` on `data-testid="task-status"` before adopting the
`sr-only` approach for that span.

**Grep result:** `manual-tests/test-cases.md` contains 29 manual test case descriptions written
as prose (steps + expected results). No test in that file — and no other file under
`manual-tests/` — contains the strings `toBeVisible`, `isVisible`, `visibility`, or
`computedStyle` in relation to `task-status`. The closest reference is TC-UI-012, which says
"Task card reflects the updated title and `Done` status badge" — a human-readable observation,
not a programmatic visibility assertion.

**Conclusion:** No existing test checks visual visibility of `data-testid="task-status"`.
The `sr-only` approach is **confirmed safe**. The span carries the correct `textContent`
(e.g. `"In Progress"`) for any `textContent`-based assertion, satisfying FR-04 and NFR-02.
This finding is documented here per the DR-06 resolution instruction.

### TASK-01 — `components/TaskCard.tsx` (Effort: M, 30–60 min)

**All changes are inside this single file.**

1. **Imports** — add `useState` and `useEffect` to the existing React import line.
   Add `TaskStatus` to the existing `import { Task } from "@/lib/types"` import.

2. **Extend `TaskCardProps`** — add one new optional field after `onDelete`:
   ```typescript
   onStatusChange?: (id: string, newStatus: TaskStatus) => Promise<void>;
   ```

3. **Destructure the new prop** in the function signature:
   ```typescript
   export default function TaskCard({ task, onEdit, onDelete, onStatusChange }: TaskCardProps)
   ```

4. **Add three local state variables** (inside the component function, before the return):
   ```typescript
   const [optimisticStatus, setOptimisticStatus] = useState<TaskStatus>(task.status);
   const [isChangingStatus, setIsChangingStatus] = useState(false);
   const [statusError, setStatusError] = useState("");
   ```

5. **Add prop-sync `useEffect`** (DR-04 — resets optimisticStatus when task.status prop
   changes externally after a dashboard re-fetch):
   ```typescript
   useEffect(() => {
     setOptimisticStatus(task.status);
   }, [task.status]);
   ```

6. **Add `handleInlineStatusChange`** async event handler (DR-02 — explicit try/catch/finally):
   ```typescript
   const handleInlineStatusChange = async (e: React.ChangeEvent<HTMLSelectElement>) => {
     const newStatus = e.target.value as TaskStatus;
     const previousStatus = optimisticStatus;
     setOptimisticStatus(newStatus);        // optimistic update (NFR-01)
     setIsChangingStatus(true);
     try {
       if (onStatusChange) {
         await onStatusChange(task.id, newStatus);
       }
     } catch (err) {
       setOptimisticStatus(previousStatus);   // rollback (FR-05)
       setStatusError(err instanceof Error ? err.message : "Failed to update status");
       setTimeout(() => setStatusError(""), 3000);
     } finally {
       setIsChangingStatus(false);
     }
   };
   ```

7. **Replace the existing status span in the JSX** — the current block:
   ```tsx
   <span
     className={`text-xs font-medium px-2 py-0.5 rounded-full ${statusColors[task.status]}`}
     data-testid="task-status"
   >
     {statusLabels[task.status]}
   </span>
   ```
   must be replaced with the following inline control group (DR-01 — testid on dedicated span):
   ```tsx
   <div className="flex flex-col gap-1">
     {/* sr-only span: textContent === statusLabels[optimisticStatus] for FR-04 / NFR-02 assertions */}
     <span data-testid="task-status" className="sr-only">
       {statusLabels[optimisticStatus]}
     </span>

     <select
       data-testid="inline-status-select"
       aria-label="Change status"
       value={optimisticStatus}
       disabled={isChangingStatus}
       onChange={handleInlineStatusChange}
       className={`text-xs font-medium px-2 py-0.5 rounded-full border-0 cursor-pointer ${statusColors[optimisticStatus]}`}
     >
       <option value="todo"        data-testid="inline-status-option-todo">To Do</option>
       <option value="in-progress" data-testid="inline-status-option-in-progress">In Progress</option>
       <option value="done"        data-testid="inline-status-option-done">Done</option>
     </select>

     {statusError && (
       <p data-testid="inline-status-error" className="text-red-500 text-xs mt-1">
         {statusError}
       </p>
     )}
   </div>
   ```

8. **All existing `data-testid` attributes** (`task-card`, `task-id`, `task-title`,
   `task-description`, `task-status`, `task-priority`, `task-assignee`, `edit-task-button`,
   `delete-task-button`) must remain in the DOM — do not touch their containing elements.

### TASK-02 — `app/dashboard/page.tsx` (Effort: S, <30 min)

**All changes are inside this single file. No new imports are needed** — `useCallback`,
`TaskStatus`, and `fetchTasks` are already present.

1. **Add `handleStatusChange`** after the existing `handleDelete` function and before the
   `filters` constant:
   ```typescript
   const handleStatusChange = useCallback(
     async (id: string, newStatus: TaskStatus): Promise<void> => {
       const res = await fetch(`/api/tasks/${id}`, {
         method: "PUT",
         headers: {
           "Content-Type": "application/json",
           Authorization: `Bearer ${token}`,
         },
         body: JSON.stringify({ status: newStatus }),
       });
       if (!res.ok) {
         const json = await res.json();
         throw new Error(json.error ?? "Failed to update status");
       }
       fetchTasks(filter);   // re-apply active filter (FR-04, Risk 2)
     },
     [token, filter, fetchTasks]
   );
   ```

2. **Pass the new prop** to `<TaskCard>` inside the `tasks.map(...)` block — add one line:
   ```tsx
   <TaskCard
     key={task.id}
     task={task}
     onEdit={(t) => { setEditingTask(t); setShowForm(false); }}
     onDelete={handleDelete}
     onStatusChange={handleStatusChange}   {/* ← new line only */}
   />
   ```

3. Do **not** touch any other part of the file.

## Out-of-Scope Reminder

Copied verbatim from `requirements.md` Section 4:

> - This story does not add inline editing for any other task field (title, priority, description, assignee).
> - This story does not introduce a new backend route or change any existing API contract.
> - This story does not change the full edit modal or its behaviour.
> - This story does not add keyboard shortcuts or drag-and-drop reordering.
> - This story does not implement bulk status updates (selecting multiple cards).
> - This story does not add a status transition workflow with enforced ordering (any status can be set from any other status).
