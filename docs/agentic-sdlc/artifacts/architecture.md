## 3. Data Model Changes

No changes are required to `lib/types.ts`. The existing `TaskStatus` union and the `status` field on `Task` are sufficient.

The only new typed surface is the extended `TaskCardProps` interface, scoped entirely to `components/TaskCard.tsx`:

```typescript
// components/TaskCard.tsx — TaskCardProps

// Existing fields — unchanged
interface TaskCardProps {
  task: Task;
  onEdit: (task: Task) => void;
  onDelete: (id: string) => void;
  // NEW — optional; existing callers without this prop continue to work unchanged
  onStatusChange?: (id: string, newStatus: TaskStatus) => Promise<void>;
}
```

**Field classification:**
- `task`, `onEdit`, `onDelete` — existing, unchanged.
- `onStatusChange` — **new, optional**. When omitted the `<select>` renders normally but no network call is made on change (safe no-op default, preserves backward compatibility).

Three component-local state variables are introduced inside the `TaskCard` function body. They are not exported, not added to any interface in `lib/types.ts`, and do not affect serialised data:

| Variable | Type | Initial value |
|---|---|---|
| `optimisticStatus` | `TaskStatus` | `task.status` |
| `isChangingStatus` | `boolean` | `false` |
| `statusError` | `string` | `""` |

No new fields are added to the `Task` interface. Seed tasks `t1`–`t5` are not modified.

## 4. API Contract Changes

### `PUT /api/tasks/:id`

The inline status control reuses the existing PUT route without any modification to the handler code.

**Request issued by the inline control:**

```
PUT /api/tasks/:id
Authorization: Bearer <token>
Content-Type: application/json

{ "status": "in-progress" }
```

Only `status` is sent. The route handler at `app/api/tasks/[id]/route.ts` applies each incoming field conditionally:

```typescript
...(status !== undefined && validStatuses.includes(status) && { status }),
```

This means sending `{ status }` alone merges cleanly with the stored record and leaves all other fields (`title`, `description`, `priority`, `assignee`) untouched.

**Response shape — unchanged:**

```json
{
  "data": { /* full Task object with updated status and updatedAt */ },
  "message": "Task updated"
}
```

**Error responses handled by the UI:**
- `401 Unauthorized` — invalid or expired token; UI rolls back select and displays inline error.
- `404 Not Found` — task deleted by another session; UI rolls back and displays inline error.
- `500` or any non-2xx — UI rolls back and displays inline error.

**Confirmation:** No existing fields removed or renamed. No new query parameters. No HTTP verb change. Route path `/api/tasks/:id` is unchanged. No changes to GET `/api/tasks` or POST `/api/tasks`.

## 5. Store Logic Changes

No changes to `lib/store.ts` are required.

- **Filter logic:** Unchanged. After a successful inline status change the dashboard calls the existing `fetchTasks(filter)`, which calls `getAllTasks(username, status, assignee)` with the active filter. This naturally removes a card from the visible list if its new status no longer matches the selected filter (FR-04 / Risk 2 from requirements).
- **Create logic:** Unchanged.
- **Update logic:** `updateTask` already spreads the incoming `data` object over the stored record and refreshes `updatedAt`. Passing `{ status: "done" }` produces the correct merged document with no side-effects on other fields.

#### Rendered structure for the status control group

```tsx
<div className="flex flex-col gap-1">
  {/* sr-only span: textContent === statusLabels[optimisticStatus]
      Preserves existing test assertions on data-testid="task-status" (FR-04, NFR-02) */}
  <span data-testid="task-status" className="sr-only">
    {statusLabels[optimisticStatus]}
  </span>

  <select
    data-testid="inline-status-select"
    aria-label="Change status"
    value={optimisticStatus}
    disabled={isChangingStatus}
    onChange={handleInlineStatusChange}
    className={`text-xs font-medium px-2 py-0.5 rounded-full border-0 cursor-pointer
                ${statusColors[optimisticStatus]}`}
  >
    <option value="todo"        data-testid="inline-status-option-todo">To Do</option>
    <option value="in-progress" data-testid="inline-status-option-in-progress">In Progress</option>
    <option value="done"        data-testid="inline-status-option-done">Done</option>
  </select>

  {statusError && (
    <p data-testid="inline-status-error" className="text-red-500 text-xs mt-1">
      {statusError}
    </p>
  )}
</div>
```

The existing `statusColors` and `statusLabels` maps already in the file are reused — no new constants are introduced.

#### Optimistic update and rollback pattern

```typescript
const handleInlineStatusChange = async (e: React.ChangeEvent<HTMLSelectElement>) => {
  const newStatus = e.target.value as TaskStatus;
  const previousStatus = optimisticStatus;

  // Step 1 — Optimistic update: reflects change in < 200 ms (NFR-01)
  setOptimisticStatus(newStatus);
  // Step 2 — Disable control to prevent overlapping requests (FR-06)
  setIsChangingStatus(true);

  try {
    // Step 3 — Delegate API call to parent; throws on non-2xx
    if (onStatusChange) {
      await onStatusChange(task.id, newStatus);
    }
    // Step 4 (success) — parent re-fetches; task prop will update via useEffect
  } catch (err) {
    // Step 5 (failure) — Rollback optimistic state (FR-05)
    setOptimisticStatus(previousStatus);
    setStatusError(err instanceof Error ? err.message : "Failed to update status");
    // Step 6 — Auto-dismiss error after 3 s (≤ 5 s limit in FR-05)
    setTimeout(() => setStatusError(""), 3000);
  } finally {
    // Step 7 — Re-enable control regardless of outcome (FR-06)
    setIsChangingStatus(false);
  }
};
```

**Prop-to-state synchronisation:** A `useEffect` re-syncs `optimisticStatus` whenever the parent supplies an updated `task.status` prop (e.g., after a re-fetch triggered by the dashboard):

```typescript
useEffect(() => {
  setOptimisticStatus(task.status);
}, [task.status]);
```

This prevents stale optimistic state if the parent supplies a new task object after a filter-driven re-fetch.

#### Error handling approach

- Errors are caught exclusively inside `handleInlineStatusChange`; no error propagates past `TaskCard` to the dashboard.
- `statusError` is a local string state; when non-empty, a `<p data-testid="inline-status-error">` renders below the `<select>`.
- The error auto-clears via `setTimeout(() => setStatusError(""), 3000)` — within the 5-second limit required by FR-05.
- No toast library is used; no page-level banner is raised; the error is card-scoped (FR-05, Non-Goal in requirements).
- Unhandled promise rejections are prevented: the `try/catch` in `handleInlineStatusChange` covers all code paths including 401, 404, 500, and network failures (FR-08).

#### Data flow through the component tree

```
DashboardPage
  ├── state: tasks[]          (re-fetched from /api/tasks after each success)
  ├── state: filter           (active status filter; passed to fetchTasks on re-fetch)
  ├── handleStatusChange      (useCallback — issues PUT, then calls fetchTasks(filter))
  │
  └── TaskCard (per task)
        ├── props: task, onEdit, onDelete, onStatusChange=handleStatusChange
        ├── local state: optimisticStatus  (drives <select> value and <span> label)
        ├── local state: isChangingStatus  (drives <select> disabled attribute)
        ├── local state: statusError       (drives inline error paragraph)
        │
        └── <select> onChange
              │  sets optimisticStatus immediately (optimistic)
              │  sets isChangingStatus=true
              │  awaits onStatusChange(task.id, newStatus)
              │     │
              │     └── PUT /api/tasks/:id  { status }
              │           ├── 2xx → fetchTasks(filter) → new tasks[] → task prop updates
              │           │         → useEffect syncs optimisticStatus = task.status
              │           └── non-2xx → throws → catch: revert optimisticStatus, set statusError
              └── finally: setIsChangingStatus(false)
```

#### Accessibility considerations

- The `<select>` carries `aria-label="Change status"` so screen readers announce its purpose independently of any visible label (NFR-05).
- Option labels are human-readable: `"To Do"`, `"In Progress"`, `"Done"` — not raw enum values (NFR-05).
- The control is keyboard-navigable: Tab to focus, arrow keys to cycle options, Enter/Space to confirm — native `<select>` behaviour, no custom JS required (NFR-05).
- While `isChangingStatus` is `true`, the `<select>` has the native `disabled` attribute, which screen readers announce as "dimmed" or unavailable (FR-06).
- The `<span data-testid="task-status" className="sr-only">` provides a programmatically associated status label for assistive technologies even when the select is collapsed.

### `app/dashboard/page.tsx`

**New state variables:** None. Existing `filter`, `token`, `fetchTasks`, and `tasks` state cover all needs.

**New handler:**

```typescript
const handleStatusChange = useCallback(
  async (id: string, newStatus: TaskStatus): Promise<void> => {
    const res = await fetch(`/api/tasks/${id}`, {
      method: "PUT",
      headers: {
        "Content-Type": "application/json",
        Authorization: `Bearer ${token}`,
      },
      body: JSON.stringify({ status: newStatus }),
    });
    if (!res.ok) {
      const json = await res.json();
      // Throw so TaskCard.handleInlineStatusChange can catch and rollback
      throw new Error(json.error ?? "Failed to update status");
    }
    // Re-fetch with active filter — removes card if status no longer matches (FR-04 / Risk 2)
    fetchTasks(filter);
  },
  [token, filter, fetchTasks]
);
```

`useCallback` is required here: without it, the function reference changes on every render of `DashboardPage`, causing all `TaskCard` instances to re-render unnecessarily.

**Updated `<TaskCard>` usage (one new prop only):**

```tsx
<TaskCard
  key={task.id}
  task={task}
  onEdit={(t) => { setEditingTask(t); setShowForm(false); }}
  onDelete={handleDelete}
  onStatusChange={handleStatusChange}   // ← additive; no existing prop changes
/>
```

**New filter controls:** None. The inline control lives on each card; the existing status filter bar is unchanged.
