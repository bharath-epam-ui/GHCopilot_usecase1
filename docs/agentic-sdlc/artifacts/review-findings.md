**Finding RV-02**
- Severity: Low
- File + Location: `components/TaskCard.tsx:53` — `setTimeout(() => setStatusError(""), 3000)`
- Issue: The timeout handle is not captured in a `useRef` and cleared in a cleanup function. If the `TaskCard` component unmounts (e.g., the card is deleted or the filter removes it) within the 3-second error window, the `setTimeout` callback will call `setStatusError("")` on an already-unmounted component. React 18 silently ignores state updates on unmounted components (the old warning was removed), so this does not produce a visible error, but it is a latent resource-usage issue and a minor code-quality deviation from the architecture document which specifies `finally` cleanup.
- Recommendation: Capture the timeout and clear it on unmount using a `useRef`:
  ```typescript
  const errorTimerRef = useRef<ReturnType<typeof setTimeout> | null>(null);
  // in catch:
  if (errorTimerRef.current) clearTimeout(errorTimerRef.current);
  errorTimerRef.current = setTimeout(() => setStatusError(""), 3000);
  // in useEffect cleanup or via a dedicated cleanup effect.
  ```
  Alternatively, clear any pending timer at the start of `handleInlineStatusChange` to handle rapid repeated errors.

**Finding RV-03**
- Severity: Low
- File + Location: `components/TaskCard.tsx:46–48` — no-op branch when `onStatusChange` is undefined
- Issue: When `onStatusChange` is not provided, the inline `<select>` still performs the optimistic state update (`setOptimisticStatus(newStatus)` on line 43) but never rolls back, because no error is thrown and no API call is made. The card will display the new status permanently until the parent re-renders the component with an updated `task` prop. The `useEffect` sync on `task.status` (line 36–38) will reset `optimisticStatus` only when the parent provides a new `task.status` value. In the actual deployed app this is benign because `onStatusChange={handleStatusChange}` is always passed, but in isolation (e.g., a Storybook story or a unit test rendering `<TaskCard>` without `onStatusChange`) the control appears to accept changes without persisting them, which can mislead.
- Recommendation: In the no-op branch, immediately reset `optimisticStatus` back to the original value so the control visibly rejects the change when no handler is wired:
  ```typescript
  if (onStatusChange) {
    await onStatusChange(task.id, newStatus);
  } else {
    setOptimisticStatus(previousStatus); // revert — no handler provided
  }
  ```
  This is a minor code clarity concern and does not block production use.
