## 2. Problem Statement

Users who need to advance a task through its lifecycle (`todo` → `in-progress` → `done`) are currently required to open the full edit modal, locate the status dropdown, select a new value, and save — a four-interaction flow for a single-field change. When managing several tasks in rapid succession on the dashboard, this detour disrupts the user's workflow. The dashboard must allow a user to change a task's status with a single interaction directly on the task card, without navigating away from the dashboard or opening any modal.

---

## 3. Goals

- Render an inline status control on every task card so the user can change status without opening the edit modal.
- Reduce the status-change interaction count from four steps (Edit → change dropdown → Save → close modal) to one (select from inline control).
- Persist the status change via the existing `PUT /api/tasks/:id` endpoint and refresh the card to reflect the new state.
- Apply optimistic UI updates so the card reflects the change immediately, with automatic rollback on API failure.
- Keep all existing task-card interactions (Edit button, Delete button, full edit modal) completely unchanged.

---

## 4. Non-Goals

- Inline editing of any field other than `status` (title, priority, description, assignee are out of scope).
- Introducing a new backend route or modifying any existing API contract, HTTP verb, or response shape.
- Changing the behaviour or layout of the full edit modal (`TaskForm`).
- Adding keyboard shortcuts or drag-and-drop status transitions.
- Bulk status updates across multiple selected cards.
- Enforced status transition ordering (any status must be selectable from any current status).
- Adding a toast/notification library (error feedback must use inline DOM elements only).

## 5. Functional Requirements

**FR-01 — Inline status control rendered on every task card**
Each task card must render an inline status control (a `<select>` element) that displays the task's current status. The control must be permanently visible on the card — no hover, click, or toggle action may be required to reveal it. The select element must carry `data-testid="inline-status-select"` and an `aria-label="Change status"` attribute.

Pass criterion: Every element with `data-testid="task-card"` in the rendered DOM contains exactly one child element with `data-testid="inline-status-select"`.

---

**FR-02 — All three status options present; current status pre-selected**
The inline control must expose all three valid status values as selectable options: `todo`, `in-progress`, and `done`. When the card renders, the option matching the task's current `status` field must be pre-selected. Each option element must carry the following `data-testid` attributes respectively:
- `data-testid="inline-status-option-todo"` for the `todo` option
- `data-testid="inline-status-option-in-progress"` for the `in-progress` option
- `data-testid="inline-status-option-done"` for the `done` option

Pass criterion: For a task card with `status: "todo"`, the select's `value` equals `"todo"` and all three options are present with the correct `data-testid` values.

---

**FR-03 — Status change triggers PUT /api/tasks/:id**
When the user selects a different status value from the inline control, the app must issue exactly one `PUT /api/tasks/:id` request with a JSON body of `{ "status": "<new-value>" }` and the current user's `Authorization: Bearer <token>` header. No other task fields may be mutated by this call.

Pass criterion: Selecting a new status on any card produces exactly one `PUT /api/tasks/:id` network request whose request body contains the `status` field set to the selected value. The request includes a valid bearer token.

---

**FR-04 — Task card visual state updates after successful API response**
After the API returns a 2xx response, the task card's accessible status indicator (`data-testid="task-status"`) must reflect the new status label (e.g., `"In Progress"` for `in-progress`). If the dashboard has a status filter active and the card's new status no longer matches that filter, the card must be removed from the visible list automatically.

Pass criterion: After changing a card's status from `todo` to `in-progress`, the element `[data-testid="task-status"]` on that card contains the text `"In Progress"`. If the `todo` filter is active, the card disappears from the task list.

---

**FR-05 — API failure rolls back the inline control to the previous status**
If the `PUT` call returns a non-2xx HTTP response (including 401, 404, 500), the inline select must revert to the status value it held before the user's selection. An error message must be rendered inline on the affected card (not as an alert or page-level banner) with `data-testid="inline-status-error"`. The error message must auto-dismiss after no more than 5 seconds.

Pass criterion: When the API returns a 500 error, the inline select value reverts to its pre-change value, and an element with `data-testid="inline-status-error"` appears on the card and disappears within 5 seconds.

---

**FR-06 — Control is disabled while an API request is in flight**
From the moment the user selects a new status until the API call resolves (success or failure), the inline select must be in a `disabled` state to prevent overlapping requests.

Pass criterion: Immediately after selecting a new status, the `<select[data-testid="inline-status-select"]>` element has the HTML `disabled` attribute. The attribute is removed after the API response is received.

---

**FR-07 — All existing task-card interactions remain fully functional**
The addition of the inline status control must not break the Edit button, Delete button, or full edit modal. All existing `data-testid` attributes on the task card (`task-card`, `task-id`, `task-title`, `task-description`, `task-status`, `task-priority`, `task-assignee`, `edit-task-button`, `delete-task-button`) must remain present in the DOM.

Pass criterion: Manual test cases TC-UI-012 (Edit an Existing Task) and TC-UI-013 (Delete a Task) pass without modification. All task-card `data-testid` attributes listed in the README remain present in the rendered DOM.

---

**FR-08 — Unauthenticated status change handled gracefully**
If the bearer token is absent or invalid at the time of an inline status change, the API returns `401 Unauthorized`. The UI must catch this response, display an inline error on the affected card (`data-testid="inline-status-error"`), revert the select to its previous value, and must not cause a page crash or unhandled promise rejection.

Pass criterion: With an invalidated token, triggering an inline status change results in a 401 response, the select reverts, and an inline error is displayed without any uncaught JavaScript error.

## 6. Non-Functional Requirements

**NFR-01 — Perceived performance**
The task card must reflect the new status value within 200 ms of the user's selection (optimistic update), irrespective of API round-trip time. The final confirmed state must be consistent with the server within 2 seconds under normal network conditions.

**NFR-02 — Backward compatibility**
No existing API route (`/api/tasks`, `/api/tasks/:id`, `/api/auth/*`), HTTP verb, response shape, or `data-testid` attribute documented in the README may be removed or renamed. All 29 existing manual test cases in `manual-tests/test-cases.md` must continue to pass without modification.

**NFR-03 — No new required Task fields**
The `Task` interface in `lib/types.ts` must not gain any new required properties. Any component-local state or helper type introduced for this feature must be optional or scoped to the component file.

**NFR-04 — Seed data immutability**
Seed tasks `t1`–`t5` in `lib/store.ts` must not be modified (content, IDs, or structure).

**NFR-05 — Accessibility**
The inline select must be keyboard-navigable (tab-focusable; arrow keys to change value; Enter/Space to confirm). It must carry `aria-label="Change status"` so screen readers announce its purpose. The option labels must be human-readable strings (`"To Do"`, `"In Progress"`, `"Done"`), not raw enum values.

**NFR-06 — No new npm dependencies**
The feature must be implemented exclusively with the existing Next.js 14, React, TypeScript, and Tailwind CSS stack. No new entries may be added to `package.json` `dependencies` or `devDependencies`.

**NFR-07 — TypeScript strict compliance**
All new or modified TypeScript code must compile without errors under the project's existing `tsconfig.json`. No `// @ts-ignore` or `any` casts may be introduced for the inline control logic.

## 7. Risks and Assumptions

**Assumption A — Partial PUT body is supported**
The existing `PUT /api/tasks/:id` route and `store.updateTask` function accept a partial body (`Partial<Omit<Task, "id" | "createdAt">>`). A call with `{ "status": "done" }` will merge cleanly with the stored record without overwriting other fields. This is confirmed by the `store.updateTask` implementation in `lib/store.ts`.

**Assumption B — onStatusChange is an optional prop**
The `onStatusChange` callback will be passed to `TaskCard` as an optional prop. When absent (e.g., in unit tests or Storybook), the select renders normally but no API call is made. This avoids breaking any existing usages of `TaskCard` that do not supply the prop.

**Assumption C — Optimistic update is permitted**
It is acceptable to update the displayed status before the API responds, provided the UI rolls back the change if the API fails. This is the agreed approach to satisfy NFR-01.

**Assumption D — Static status badge is replaced, not duplicated**
The existing static status badge (previously the sole element with `data-testid="task-status"`) is replaced by a visually equivalent element that wraps or accompanies the inline select. The `data-testid="task-status"` attribute is retained on a sibling element (e.g., a hidden `<span>`) whose text content equals the human-readable status label, preserving existing test assertions.

**Risk 1 — Race condition on rapid successive changes**
If a user changes status twice before the first API call resolves, the second optimistic update may conflict with a rollback from the first failed call. Mitigation: disable the control while a request is in flight (FR-06), which prevents a second change from being initiated until the first resolves.

**Risk 2 — Filter desync after inline status change**
When the dashboard is filtered (e.g., showing only `todo` tasks) and a card's status is changed inline to `in-progress`, the card must be removed from the visible list. If the parent component does not re-apply the filter after state update, the card will remain visible in an inconsistent state. Mitigation: trigger a `fetchTasks(filter)` call in the `handleStatusChange` callback in the dashboard after each successful API response.

**Risk 3 — Visual redundancy between status badge and select**
If both the static badge and the new select are rendered simultaneously, the card becomes visually cluttered and the user may be confused about which control is authoritative. Mitigation: use a single element (the select) as both the visual indicator and the interactive control.

## 8. Open Questions

**OQ-01 — Replace vs. coexist for the static status badge**
Should the inline status select completely replace the existing static status badge on the card, or should both coexist? Replacing keeps the card clean; coexisting minimises DOM change risk.
_Default assumption if unanswered before implementation:_ The select replaces the static badge. A visually hidden `<span data-testid="task-status">` is retained alongside the select so that existing test assertions on `task-status` text content continue to pass.

**OQ-02 — Inline error display vs. global toast**
Should status-change errors be shown inline on the affected card, or via a global toast/notification? No toast library is present in the codebase.
_Default assumption if unanswered:_ Error is displayed inline on the card, below the select, with `data-testid="inline-status-error"`, auto-dismissed after 3 seconds.

**OQ-03 — Re-fetch vs. local state update after successful change**
After a successful status change, should the dashboard re-fetch the full task list from the API (ensuring server consistency) or update the task in local React state only (faster, avoids a round-trip)?
_Default assumption if unanswered:_ Re-fetch the task list so the displayed data always reflects server state. The optimistic update covers perceived latency.
